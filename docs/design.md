# えんメイト（個人開発版）設計書

作成日: 2026-09-30

## 0. この文書について

- インターンで作った「えんメイト」を、個人開発で作り直すための設計書です。
- インターンの仕様書（リポジトリの外の `NAVITIME Internship\specification.md`）は参考にしますが、公開は許可されていません。この設計書では仕様書の文章を写さず、自分の言葉で書き直します。仕様書そのものは変更しません。
- このアプリは、就活で見てもらうために GitHub で公開する前提で作ります。この設計書も、自分の言葉で書いたものなのでリポジトリに入れます（§9.4）。
- 「未確認」と書いた項目は、確認がとれるまで推測で決めません。

---

## 1. 目的と利用者

### 1.1 解きたい課題
車で遠くの試合やライブへ行くとき、次のことを1か所で決められるようにします。
- いつ家を出れば、会場に間に合うか
- どこで休憩し、どこに寄り、どこに泊まるか
- 当日、今どこにいて、この先どうなりそうか

### 1.2 利用者と使い方
| 項目 | 内容 |
|---|---|
| 利用者 | 本人と、所属する遠征サークルのメンバー |
| 計画を立てる人 | ほぼ1人（同時に複数人が使うことはほぼない） |
| 頻度 | 遠征は多くて月3〜4回 |
| 端末 | 計画はPCまたはスマホ。当日はスマホ |
| 利用の範囲 | 非商用。サークルの外には公開しない |

### 1.3 きっかけとなった実体験
新潟から岡山へ遠征し、香川に泊まったことがある。香川は新潟→岡山のルートでは通らないため、「通る都道府県」だけで宿や寄り道を探す作りでは候補に出てこない。通らない都道府県も選べることを、この設計でも必須にする。

## 2. 基本方針

1. **API の呼び出し回数を減らす**: NAVITIME の無料枠は月500アクセスです。入力中や時間の経過で呼ぶ処理をなくし、利用者の操作1回につき決まった回数だけ呼びます（どの操作で何回呼ぶかは §6.1）。失敗しても自動では呼び直しません。一度取った結果は保存して使い回します。
2. **無料で使えるサービスで組む**: NAVITIME の無料枠で使えない機能は、無料の別サービスに置き換えます。代わりがないものは作りません。
3. **秘密を公開しない**: API キーとインターンの仕様書は、GitHub に載せません。
4. **小さく作って、段階的に足す**: 日帰りのプランから作り、宿泊や当日ページは後から足します（§11）。
5. **GitHub で公開し、就活で見てもらう**: コードは最初から公開リポジトリに置きます。見る人がアプリを動かさなくても、何を作り、何を判断したかが分かるようにします（§9.4）。

| 機能 | 判定 | 使うもの | 段階 |

| 地図の表示 | 作る | OpenFreeMap（Positron）＋ MapLibre（2026-10-02 に地理院タイル ＋ Leaflet から変更） | 1 |

| 宿の検索（会場周辺、名前で検索） | 作る | NAVITIME スポットカテゴリ検索・スポット検索（仕様書どおり） | 3 |
| 宿の予約リンク | 後回し（2026-10-01 本人が決定） | 楽天トラベル API の予定 | 3 のあと |
| 通る都道府県・通らない都道府県で探す | 作る | NAVITIME 逆ジオコーディング・住所検索（RapidAPI の NAVITIME Geocoding を購読して使う。2026-10-01 本人が決定） | 3 |
| PCで作ったプランをスマホで開く | 作る | プランのファイル書き出し・読み込み | 4 |
| スマホからの利用（公開サーバー） | 作る | Vercel | 4 |
| 当日ページ（現在地からの再計算、次のSA/PA） | 作る | ブラウザの位置情報 ＋ ルート検索 | 5 |
| 天気 | 作る | Open-Meteo | 5 |
| 会場周辺の駐車場の場所 | 作る | OpenStreetMap（Overpass API） | 5 |
| 渋滞予測込みの時刻 | 作らない | RapidAPI では渋滞情報（VICS・プローブ）を使えないと、RapidAPI の API 概要に明記されている（2026-09-30 確認） | — |
| 道の混雑（この先の区間ごとの遅れ） | 作らない | 同上 | — |
| 駐車場の空き状況 | 作らない | 無料で使える代わりがない | — |
| プランをメンバーとサーバーで共有 | 作らない | 計画する人が1人なので、ファイルの受け渡しで足りる | — |

### 3.2 インターン版から変えた点と理由
就活で「自分が何を判断したか」を説明するための記録も兼ねます。

| インターン版 | 個人開発版 | 理由 |
|---|---|---|
| 条件を変えると自動で再計算 | 時刻などの条件は「計算する」ボタンを押した時だけ計算（立ち寄り先・宿泊先の変更は、押した操作1回につきその区間だけ計算。§5.3・§6.1） | 月500アクセスに収めるため |
| 名前の入力中に候補を出す（入力補完） | 検索ボタンを押した時だけ検索 | 1文字ごとに呼ぶと枠を使い切るため |
| 通る都道府県を最大40地点で調べる | 最大8地点に間引き、結果を保存して使い回す | 同上 |
| 当日ページで5分ごとに自動で再計算 | ボタンを押した時だけ再計算 | 同上 |
| 駐車場の空き状況を5分ごとに表示 | 作らない（場所だけ表示） | 無料の代わりがないため |
| 宿の予約ページを、予約サイトのページを読み取って探す | 楽天トラベル API で予約ページへつなぐ（未着手）。宿の候補は仕様書どおり NAVITIME の場所検索で探す | ページの読み取りは規約上のリスクがあるため |
| NAVITIME の地図 | OpenFreeMap（はじめは地理院タイル） | 無料枠で地図が使えるか確認できないため。地理院タイルは線が多くルートが埋もれるため、2026-10-02 に OpenFreeMap へ変更（§10.7） |
| 渋滞予測込みの時刻、道の混雑 | 渋滞を考慮しない時刻を出し、そのことを画面に明記する | RapidAPI では渋滞情報を使えないため |
| ルートの線を、閲覧のたびに検索し直す | ルート検索のときに `shape=true` で形も一緒に受け取り、プランに保存する | 別の API（`/shape_car`）で取り直すと、そのたびにアクセスを使うため |
| 開発サーバー（localhost）でしか動かない | Vercel に置き、https で開く | スマホで位置情報を使うには https が必要なため |
| プランはブラウザの中だけに保存 | ブラウザに保存し、ファイルで書き出し・読み込みもできる | PCで作ったプランを当日スマホで開くため |

## 4. 全体の構成

```
[ブラウザ（PC・スマホ）]
  画面（Nuxt / Vue 3）
  保存: プラン、APIの結果の使い回し、今月の使用回数 … localStorage
      │
      │ 合言葉つきで呼ぶ
      ▼
[Vercel のサーバー側（Nuxt のサーバールート）]
  APIキーを持ち、外部サービスへ中継する
      │
      ├─ NAVITIME（RapidAPI 経由）… ルート・スポット・カテゴリ・逆ジオ・住所
      └─ 楽天トラベル API … 宿
[ブラウザから直接呼ぶ（キー不要）]
  ├─ Open-Meteo … 天気
  ├─ OpenFreeMap … 地図（ベクトルタイル。ブラウザから直接読む）
  └─ Overpass API … 駐車場の場所
```

### 4.1 技術の選択
| 項目 | 選択 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型でデータの形を固定し、AIが書いたコードの誤りに気づきやすくする |
| 画面とサーバー | Nuxt（Vue 3） | インターンで使った Vue 3 と同じ書き方なので、本人がコードを読んで説明しやすい。画面とAPIの中継を1つの仕組みで作れ、Vercel にそのまま置ける |
| 地図 | MapLibre GL JS ＋ OpenFreeMap（Positron。地名は日本語だけにする） | 無料で、登録・APIキー・回数の上限がなく、商用利用もできる（出典の表示が必要）。灰色の濃淡だけの地図なので、ルートの線が目立つ（2026-10-02 に Leaflet ＋ 地理院タイルから変更。§10.7） |
| 置き場所 | Vercel（無料プラン） | https で公開でき、APIキーをサーバー側に置ける |
| 保存 | localStorage ＋ JSON ファイルの書き出し・読み込み | 利用者が1人なのでデータベースは不要 |
| テスト | Vitest（計算の部分）、実機での操作確認 | §10 |

この選択で決定です（§12.2）。最初は Next.js（React）でひな形を作りましたが、インターンで Vue 3 を使っていたことから、2026-10-01 に Nuxt へ切り替えました。

プランをブラウザ（localStorage）に保存するので、画面はブラウザ側だけで組み立てます（Nuxt の `ssr: false`）。サーバー側で動くのは、API の中継だけです。

Nuxt に切り替えた直後、パッケージを見つけられずに起動に失敗しました。最初はフォルダの経路に日本語が含まれているためと考え、親フォルダの名前を英語に変えましたが、直りませんでした。握りつぶされていたエラーを表示させて調べたところ、原因は `package.json` の先頭に BOM（文字コードを示す、目に見えない印）が付いていて、JSON として読めなかったことでした。BOM を取り除くと起動しました（2026-10-01 に確認）。日本語の経路でも型の準備（`nuxt prepare`）は通ることを確かめています。開発サーバーの起動までは、日本語の経路では試していません。

### 4.2 外部サービスを呼ぶ部分の分け方
サービスごとにファイルを分け、画面からはサービス名を意識せずに呼べるようにします。あとで別のサービスに差し替えるとき、変えるのはそのファイルだけで済みます。

| 役割 | ファイル（予定） | 今の中身 |
|---|---|---|
| ルート検索 | `app/services/route.ts` | NAVITIME ルート検索（車） |
| 場所の検索 | `app/services/place.ts` | NAVITIME スポット検索・カテゴリ検索 |
| 住所・都道府県 | `app/services/area.ts` | NAVITIME 逆ジオコーディング・住所検索 |
| 宿 | 候補は `app/services/place.ts`（NAVITIME カテゴリ検索）、予約は `app/services/hotel.ts`（予定） | 予約は楽天トラベル API の予定（未着手） |
| 天気 | `app/services/weather.ts` | Open-Meteo |
| 駐車場 | `app/services/parking.ts` | Overpass API |

API キーを使う中継は、サーバー側の `server/api/` に置きます。

## 5. 画面

### 5.1 画面の一覧
| URL | 画面 | 段階 |
|---|---|---|
| `/` | トップ（保存したプランの一覧） | 1 |
| `/plans/new` | プランの作成 | 1 |
| `/plans/{id}` | プランの閲覧 | 1 |
| `/plans/{id}/edit` | プランの編集 | 1 |
| `/plans/{id}/today` | 当日ページ | 5 |

### 5.2 一覧
- 見た目は、プランを観戦チケットに見立てた夜の画面（2026-10-01 に本人が選んだ B 案。見本はリポジトリの外の `NAVITIME Internship\個人開発\トップ画面案B_完了済み.html` の「決定案」）。
- いちばん上は「夜の高速を走り、地平線の先に会場の照明が光る」絵にし、言葉は「ROAD TO THE VENUE」「会場まで、一本道。」にします（2026-10-01 に本人が決定。見本はリポジトリの外の `NAVITIME Internship\個人開発\トップ画面案C_文言と背景.html` の背景1・文言A）。はじめは B 案のナイター照明のスタジアムと「AWAY DAYS」「スタンドまで、一本道。」だったが、サッカーだけのアプリに見えるため、試合にもライブにも合う「会場」の言葉にし、遠征らしさを出すために道を描いた。
- すべての区間が終わる日（下の段落）が今日以降のプランは「これからの遠征」として、試合日が近い順にチケットで並べます。チケットには試合日・プラン名・出発地→会場・家を出る時刻と帰り着く時刻（前日・翌日なら「前日」「翌」を付ける）を出し、半券の部分に「あと○日」（当日は「今日」、試合日を過ぎて帰り着くまでは「遠征中」。2026-10-01 本人が決定）を出します。押すと閲覧ページへ移ります。
- 遠征が終わったプランは「遠征完了済み」に移します。完了済みは最初はたたんであり、半券の束と枚数だけを出します。開くと、行った回数・走った距離・高速料金の合計と、年ごとの半券（新しい順）が出ます。完了済みへ移すのは、すべての区間が終わった日（最後の区間の到着日。後泊なら翌日の帰り、夜中に家へ着けばその日）の翌日です（2026-10-01 本人が決定）。まだ計算していないプランは、試合日に後泊の泊数を足した日で決めます。
- 泊まる遠征は、チケットの日付の横に「前泊」「後泊」「前泊・後泊」を出します（仕様書 §4.4 の表記）。
- チケットの色は1色です。試合とライブの区別やチームの色は、今は持ちません（必要になったら作成画面に入力欄を足す）。
- 各プランに「当日ページを開く」を出します（段階5）。
- 「プランを読み込む」で、書き出したファイルからプランを追加できます（段階4、2026-10-02 実装）。同じプラン（同じ ID）がすでにあれば、両方の保存日時を見せて上書きしてよいか確かめます。えんメイトの書き出しファイルでないもの・中身が欠けたものは読み込まず、理由を出します。
- 画面の下に、今月の NAVITIME の使用回数の目安を出します（§6.3）。

### 5.3 プランの作成・編集
インターン版の仕様書（§4.2）の流れをベースにします（2026-10-01、本人の指示）。

1. **おおまかなプラン**: 出発地（自宅など）、到着地（会場）、行く日（試合日）、到着予定時刻の4つだけを入れ、「おおまかなプランを作成」で往復の時刻を計算して「行きを決める」へ進みます。試合の終了時刻は初期値（17:00）のままにし、到着予定時刻以前なら到着の4時間後（日付をまたぐなら 23:30）に仮置きします。会場の検索結果は、スタジアム・球場・ホール・劇場・ライブハウス・競馬場などの施設に絞ります（種類のない場所は残す）。
2. **① 行きを決める**: 上に「① 行き ② 帰り」のタブを出し、いまの段階を塗り、済んだ段階に ✓ を付けます。行きの条件を1行で要約し（例: 新潟駅 → 長野Uスタジアム / 10月10日・12:00 着・当日に出発）、「ほかの条件を変える」で出発地・到着地・行く日・休憩間隔を変えられます。到着予定時刻は、行きの区間のカードのいちばん上で入れます。下に「帰り（仮）」として帰りの時刻を小さく出します。「行きを確定して、帰りを決める」は、行きが今の条件で計算済みのときだけ押せます。
3. **② 帰りを決める**: 行きは1行（出発時刻 → 会場の到着時刻）にたたみ、「行きを変える」で戻れます（戻っても帰りの入力は残る）。帰りの要約（試合終了・退場時間・日帰り）を出し、試合の終了時刻と退場・出庫にかかる時間（0〜180分、5分刻み）は、帰りの区間のカードのいちばん上で入れます。
4. **区間のカード**: 区間の番号・区間名・出発地 → 到着地、時刻の入力欄、出発・到着の時刻（計算で決まった側を色で目立たせる）、「運転 ○時間○分・距離・高速 ¥○」、立ち寄り先の一覧、「おすすめ休憩地（○件）」（§7.2）。
5. **立ち寄り先**（仕様書 §4.5）: 区間ごとに持ち、並び順どおりに寄ります。各立ち寄り先に番号・種類・名前・NAVITIME のページへのリンク・滞在時間（0〜720分、10分刻み）・↑↓・✕ を出します。滞在時間の初期値は 観光90分・食事60分・休憩30分・その他30分です。追加・並べ替え・滞在時間・削除をすると、変更が止まってから0.6秒後に、その区間だけを計算し直します。
6. **立ち寄り先を追加する画面**: 「＋立ち寄り先を追加」で開きます（スマホは下から出るシート、PC は左の列に重ねて出し、右の地図は見えたまま）。タブは「周辺観光」（約10km以内）「周辺グルメ」（約3km以内。運転するので居酒屋・バーなどのお酒と宅配は外す）「通る都道府県・検索」（下の 12）。最初は6件、「もっと見る」で残りを出します。追加しても閉じず、「「○○」を○番目の立ち寄り先に追加しました」と出します。立ち寄り先があるときは「寄る順番」を選べ、初期値は行きが最後（到着の直前）、帰りが1番目（出発の直後）です。種類は場所の種類から決めます（SA/PA は休憩、グルメは食事、観光・文化施設は観光、それ以外はその他）。
7. **遠征のまとめと保存**: 帰りの区間のカードの下に、枠を青くして出します。運転時間・高速料金（ETC）の合計、「プラン名（空欄なら「（会場名） 遠征 （M/d）」）」、「このプランを保存する」（編集では「変更を上書き保存する」）。押せないときは理由（計算し直しています／入力の誤り／計算できなかった区間がある／今の条件で計算し終わると保存できます）を出します。
8. **保存せずに離れるとき**: 「プランはまだ保存していません。入力した内容を捨ててページを移りますか？」（編集では「変更はまだ保存していません。変更を捨ててページを移りますか？」）を出します。
9. **編集**: 条件と行きを確定済みにした状態（帰りを決める段階）で開きます。
10. **地図**（仕様書 §4.11）: おおまかなプランではプラン全体、行きの段階では行き、帰りの段階では帰りのルートを描きます。休憩候補には「休1」などの印と、常に出しておく吹き出し（「休憩候補（SA）・11:15頃」・名前・「＋ここで30分休憩する」）を付け、押すと休憩として入れます。
11. **宿泊**（仕様書 §4.4。まずは前泊・後泊それぞれ1泊まで。§12.2）:
    - 前泊: 「行きを決める」に欄を常に出し、「＋前日に泊まる（前日の宿泊先を追加）」で前泊にします。欄には前日の宿泊先、「宿泊先を選ぶ」、「✕ 前泊をやめる」を出します。行きは「前日に宿泊先へ」（前日に宿泊先へ着く時刻から逆算。初期値 18:00）と「当日の行き」（宿泊先 → 会場）の2区間になります。
    - 後泊: 「帰りを決める」に「その日に帰る」「試合後に泊まる（後泊）」を出します。前泊もしているときは「前日と同じ宿泊先に泊まる」（初期値オン）を出し、オフにすると試合後の宿泊先を選べます（試合後の宿泊先を選ぶと自動でオフ）。帰りは「試合後に宿泊先へ」と「翌日の帰り」（翌日に宿泊先を出る時刻から。初期値 10:00）の2区間になります。
    - 後泊すると、タブは「① 行き ② 試合後の移動 ③ 翌日の帰り」になり、帰りの区間を1本ずつ確定します。いま決めていない「翌日の帰り」は、時刻だけを点線の枠で出し、「前の段階を確定すると、立ち寄り先などを決められます」と添えます。確定した区間は1行にたたみ、「変える」で戻れます。
    - 宿泊先が未設定の区間は、点線の枠に区間名・「宿泊先（未設定）」・時刻の欄・理由を出し、計算しません。行きと帰りは別々に確かめるので、片方の宿泊先が未設定でも、もう片方は計算・確定できます（仕様書 §4.7）。
    - 宿泊先を選ぶ画面（立ち寄り先を追加する画面と同じ形）: 「会場周辺」は、会場から約5km以内のホテル・旅館・温泉旅館・ペンションなどを近い順に出します（日帰りの温泉とファッションホテルは除く）。「検索」は名前で全国から探します。最初は6件、「もっと見る」で残り。「ここに泊まる」で設定して閉じ、選んである宿は「✓ 宿泊先に設定済み」と出します。各候補に「NAVITIMEで詳しく見る↗」を出します。
    - 宿泊をやめて区間がなくなるときは、なくなる区間の立ち寄り先を、残る区間へ走る順につなげて移します。
    - 立ち寄り先のおすすめを探す場所は、仕様書 §4.5 の表のとおり区間ごとに変えます（前日の区間は前日の宿泊先、当日の行きと試合後の区間は会場、翌日の帰りは出発する宿泊先の周辺）。
12. **通る都道府県**（仕様書 §4.4・§4.5。2026-10-01 実装）: 宿泊先を選ぶ画面の「通る都道府県」タブと、立ち寄り先を追加する画面の「通る都道府県・検索」タブ。
    - 調べるルート: 宿泊先は、前泊なら自宅→会場、後泊なら会場→自宅（立ち寄り先は入れない）。立ち寄り先は、その区間の出発地→到着地。同じ出発地・到着地の計算結果があればその線の形を使い、なければルート検索します（おおまかなプランと同じ条件なので、ふつうは保存した結果を使えて呼ばない）。
    - 通る都道府県: ルートの線から、始点から終点まで同じ間隔で、15km以上あけて最大8地点を選び、1地点ずつ逆ジオコーディングで都道府県・市区町村を調べます。通る順にボタンで出し、同じ都道府県は最初に通ったところで1回だけ出します。住所が分からない地点は除きます。タブを開いたときに調べ、都道府県は自動では選びません（選ぶまで場所検索を呼ばない）。
    - ルート沿い: その都道府県だった地点の前後（となりの地点との中間まで）を、その都道府県を走る範囲とみなし、約20kmごとに最大3か所を中心にして、半径10kmで種類の検索をします。住所がその都道府県で、ルートの線から10km以内のものだけを、ルートから近い順に出します（カードは「ルートから ○km」）。
    - 宿泊先: 都道府県を選ぶと「市区町村」のプルダウンを出します（住所検索。政令指定都市は区ごと）。先頭は「○○のルート沿い」、続けて「ルートが通る市区町村」（住所を調べた地点の市区町村）と「そのほかの市区町村」に分けます。市区町村を選ぶと、その中心から半径10kmで、住所がその市区町村の宿を中心から近い順に出します（「○○市の中心から ○km」）。ボタンの下の「そのほかの都道府県」で、通らない都道府県を地方ごと（北海道・東北／関東／中部／近畿／中国／四国／九州・沖縄）に選べます。通らない都道府県は、市区町村を選ぶまで「都道府県名 ホテル」の100件から住所がその都道府県の宿だけを人気の順に出し（カードは種類と住所）、プルダウンの先頭は「○○全体（人気の宿泊先）」にします。
    - 立ち寄り先: 入力欄が空のときは、都道府県を選び、探す範囲（「ルート沿い」「○○全体」）と「観光」「グルメ」を切り替えます。全体は、観光は都道府県名、グルメは「都道府県名 グルメ」で100件を検索し、住所がその都道府県で種類が合うものだけを残します（グルメは名前に都道府県名が入っているだけのものを除く）。言葉を入れて検索すると、ボタンの先頭に「全国」を足し、都道府県を選んでいれば「都道府県名 言葉」で100件を検索して住所がその都道府県のものだけを、全国なら言葉のまま探します。検索している間は、探す範囲と種類の切り替えを出しません。入力欄の「✕」で言葉を消すと、おすすめに戻ります。入れる種類は場所の種類から決めます。

仕様書と変えたところ（理由つき）:
- 条件（時刻・出発地・会場など）を変えたときは自動で計算せず、区間のカードの「計算し直す」を押したときだけ計算します（月500回の無料枠のため。§3.2）。立ち寄り先の変更は、仕様書どおり自動で計算し直します（押した操作1回につき1回なので）。
- 編集で開いたときは、保存した結果をそのまま使い、すぐには計算し直しません（同上）。
- 場所の検索は、入力補完を出さず、「検索」を押したときだけ探します（§3.2）。検索結果は欄の下に出します（仕様書では重ねて出す画面）。
- 通る都道府県を調べる地点は、仕様書の「15km以上の間隔で最大40地点程度」を最大8地点にしました（§3.2。逆ジオコーディングも月500回のため）。長いルートでは地点の間隔が広くなるので、短い距離だけ通る都道府県はボタンに出ないことがあります。そのときは「そのほかの都道府県」から選べます（宿泊先）。立ち寄り先は、言葉を入れれば全国から探せます。
- ルート沿いを探す中心は、仕様書の「ルート上の地点から半径10km以内」を、都道府県ごとに最大3か所の中心で探す形にしました（場所検索の回数を抑えるため）。そのため、都道府県の中を長く走るルートでは、中心と中心のあいだの場所が出ないことがあります。
- 宿泊の変更（泊まる・やめる・宿泊先を選ぶ・同じ宿泊先にする）は、押した操作1回なので、立ち寄り先と同じく、出発地か到着地が変わった区間だけを自動で計算し直します。前日に着く時刻・翌日に出る時刻は、ほかの時刻と同じく「計算する」「計算し直す」を押したときだけ計算します。
- 宿泊先を選ぶ画面には、仕様書にない「検索」タブ（名前で全国から）も残しました。宿の名前が分かっているときに、都道府県を選ばずに探せるようにするためです。ほかのタブと同じく、宿でない場所（駅・店など）は出しません（2026-10-01 レビューで決定）。
- 宿泊先の予約の条件（チェックイン・人数・部屋数）と予約リンクは後回しにしました（2026-10-01 本人が決定）。今は各宿に「NAVITIMEで詳しく見る↗」だけを出します。
- 候補のカードを押して地図にその場所を出す動きは、立ち寄り先の追加画面と同じく、まだ作っていません。
- スマホでは、地図をページの下に常に出します（仕様書は「地図で見る」で開くシート）。

仕様書にない追加（本人が決定、2026-10-01）:
- **寄る順番を最適にする（提案）**: 立ち寄り先が2か所以上ある区間のカードに出します。押すと、NAVITIME の最適順（`via_type=optimal`）で1回だけ検索し、応答の経由地の座標（渡した座標がそのまま寄る順に入る。2026-10-01 確認）で元の立ち寄り先と対応づけて並べ替えます。その結果を、並べ替えた順番での計算結果として保存するので、並べ替えたあとの計算し直しでは呼びません。並べ替えたままの間は「元の順に戻す」を出し、戻すときは並べ替える前の結果を使います（呼ばない）。今の順番が最適なら「今の順番が最適でした」と出します。NAVITIME の最適順は経由地10か所・滞在の合計300分までなので、超えるときは押せなくして理由を出します。検索している間に立ち寄り先を変えたら、その変更を残して並べ替えません。

### 5.4 閲覧
- 保存したときの計算結果だけを表示し、ルートは検索し直しません。
- 地図にルートの線を描くには形のデータが要ります。保存するときに、ルートの形も間引いて一緒に保存し、閲覧で API を呼ばないようにします（インターン版では閲覧時に検索し直していた）。
- 見出し（プラン名、試合日・宿泊の表記（日帰り／前泊／後泊／前泊・後泊）、出発地 → 会場、編集・削除）、合計の運転時間・距離・高速 ETC 料金、「保存した時点（M/d HH:mm）に計算した…時刻です」の注記を出します（仕様書 §5.1）。
- 「行き」「帰り」の2枚のカードに、最初の出発と最後の到着、その方向の運転時間・距離・高速料金を出します。前泊・後泊で区間が増えても、方向ごとに1枚にまとめます（行き = 前日に宿泊先へ＋当日の行き、帰り = 試合後に宿泊先へ＋翌日の帰り）。カードを押すと、その方向のルートを地図に出し、出している方は背景を青くします。右上に「🗺 地図に表示中」「🗺 押すと地図に表示」を出します。地図の「全体を表示」で往復のルートに戻ります（仕様書 §5.2・§5.5）。
- 「▼ 詳しいタイムラインを見る」で、日付ごとに 🚗 出発（区間名）・⭐ 立ち寄り（〜出る時刻、詳細へのリンク）・📍 到着を出し、帰りは最初に 🏟 試合終了を出します。宿泊先に着くところは「（宿泊）」と NAVITIME のページへのリンクを付けます。休憩候補はタイムラインにも地図にも出しません（休憩は作成時に立ち寄り先として決めるため）。
- 宿泊先を、泊まる順（前日・試合の夜）に出します。前日と同じ宿に2泊するときは1つにまとめます（仕様書 §5.4）。予約リンクは、まだ出しません。
- 「ファイルに書き出す」で JSON ファイル（`enmate_試合日_プラン名.json`）として保存できます（段階4、2026-10-02 実装）。ファイルには、計算結果と線の形も含めたプランをそのまま入れるので、読み込んだ端末では API を呼ばずに閲覧できます。形は `{ app: "enmate", schemaVersion: 1, exportedAt, plan }`（別のアプリの JSON と見分けるため `app` を付ける）。

### 5.5 当日ページ（段階5）
- 今どの区間にいるかを、現在時刻とプランの時刻から判断します。
- 「現在地から再計算」ボタンを押した時だけ、現在地から目的地までを検索し直します。自動では呼びません。
- 表示するもの: 着く時刻の見込み、次の SA/PA、会場周辺の駐車場の場所、これからの天気。

### 6.2 結果の使い回し
- API の結果を、呼んだときの条件（出発地・目的地・日時など）をキーにして localStorage に保存します。
- 同じ条件でもう一度呼ぼうとしたときは、保存した結果を使います。
- 保存しておく期間の目安: ルート検索は1日、場所・カテゴリ検索は30日、逆ジオコーディング・住所検索は90日（住所はめったに変わらないが、保存領域を使い続けないように）。
- 保存領域がいっぱいでプランを保存できないときは、使い回し用のデータ（消しても検索し直せる）を消してから、もう一度だけ保存します。

### 6.3 使用回数の目安
- NAVITIME を呼ぶたびに、その月の回数をブラウザに記録し、一覧の下に「今月 ○/500」と出します。
- 他の端末で使った分は数えられないので、あくまで目安です。
- 400回を超えたら注意を出します。
- RapidAPI は応答ヘッダー（`x-ratelimit-requests-remaining`）で今月の残り回数を返すことを確認しました。NAVITIME を呼んだときはこの値を記録し、ブラウザで数えた回数より優先して表示します。
- RapidAPI では、ルート検索（NAVITIME Route(car)）・場所検索（NAVITIME Spot）・住所の検索（NAVITIME Geocoding）は別々の API で、購読も無料枠も別です。どれも上限は月500回でした（2026-10-01 に応答ヘッダー `x-ratelimit-requests-limit` などで確認）。使用回数は API ごとに分けて表示します。失敗した呼び出し（HTTP 400 など）も1回に数えられます（2026-10-01、Geocoding で確認）。
- 使用回数は、一覧の下と、作成・編集ページの下に出します（検索するのは作成・編集ページなので、その場で増えたことが分かるように）。

### 6.4 見積もり（試算）
前泊ありの3区間、立ち寄り先の検索20回程度、当日の再計算が往復で20〜30回を前提にした試算です。実際の回数は段階1を作ったあとに数えて、この表を更新します。

| 場面 | 回数 |
|---|---|
| プラン作成のルート計算（線の形を含む） | 20〜30 |
| 場所・観光・グルメの検索 | 約20 |
| 通る都道府県の判定 | 10〜20 |
| 当日の再計算 | 20〜30 |
| **1回の遠征** | **約70〜100** |
| **月4回** | **約280〜400** |

RapidAPI で `shape=true` が使えなかった場合は、`/shape_car` を区間ごとに1回ずつ呼ぶことになり、1回の遠征で5〜10回増えます。

段階1で実際に数えた回数（2026-10-01、新潟駅 → 長野のスタジアムの日帰りプランを1件作って保存）:

| 操作 | ルート検索 | 場所検索 |
|---|---|---|
| 出発地と会場を検索して選ぶ | 0 | 2 |
| 「計算する」を押す（連打しても同じ） | 2 | 0 |
| 到着時刻を変えて、元に戻す | 0 | 0 |
| 保存・閲覧・再読み込み・編集して上書き保存 | 0 | 0 |
| **合計** | **2** | **2** |

`shape=true` は使えたので、線の形のための追加の呼び出しはありません。線の形は、ずれが30m以内に収まるように点を間引いて保存します（約213kmのルートで約2,900点 → 約290点。プラン1件の保存データは約15,000文字）。

## 7. 計算の決まり

### 7.1 区間の組み立て
- 行きは「着きたい時刻」から逆算して出発時刻を決めます。帰りは「出る時刻」から到着時刻を決めます。
- 区間は、日帰りなら「行き」「帰り」の2つです。前泊すると「自宅→宿」「宿→会場」、後泊すると「会場→宿」「宿→自宅」に分かれます。
- 帰りの出発時刻は「試合の終了時刻＋会場を出るまでの時間」です。
- 行きは `goal_time`（到着時刻）、帰りは `start_time`（出発時刻）を指定して検索します。公式仕様では、この2つは同時に指定できません。
- 立ち寄り先は `via`（経由地）で渡し、滞在時間も一緒に指定します。
- RapidAPI 版でもこれらが使えることを、2026-09-30 に試して確認しました（§12.1）。新潟駅から岡山へ、10/3 12:00 着・金沢駅に30分寄る条件では、出発は 02:18 と返ってきました。
- 応答の時刻は秒まで入っています（例: 09:20:22）。画面には分までを出し、秒は切り捨てます。
- 高速料金は、応答の `summary.move.fare` の `unit_1025_2` を使います。公式仕様では、`1025` が ETC 搭載車、末尾の `2` が普通車です（`1024` は現金、末尾 `1` は軽自動車・二輪）。
- 公式仕様には「経路全体の ETC 料金は、時間帯や曜日の割引を適用したあとの金額」とありますが、土曜日（2026-10-10）の検索で返ってきた `unit_1025_2` は現金と同じ 4,920 円で、休日割引の金額（3,440 円）にはなっていませんでした。そのため画面には「休日や深夜の割引は反映されないことがあります」と書きます。割引後の金額を出すかは、あとで決めます（§12.1）。

### 7.2 休憩地の提案
- RapidAPI 版では、連続運転時間（`continuous_driving_time`）を指定しても、休憩地点の候補（`recommend_spot`）は返ってきませんでした（2026-09-30 に試して確認）。公式仕様でも、この項目は大型車向けで、120〜240分しか指定できません。
- そのため、`options=turn_by_turn` と `divide_with=sa.pa`（複数の値はピリオドで区切る）で SA/PA の情報を受け取り、運転が休憩間隔を超えないように自分で選びます。応答の中の SA/PA の地点には `sapa_type`（"SA" か "PA"）と `sapa_id` が付いており、その地点に着く時刻は直前の移動区間の `to_time` で分かります。
- 選び方は仕様書 §4.8 のとおりです（2026-10-01）。
  - 休憩間隔は 1時間30分／2時間／2時間30分 から選びます（初期値2時間）。
  - 前の休憩（出発）から30分以上走ったところで、休憩間隔ぎりぎり（残り40分以内）まで走れる SA を優先し、なければ範囲内でいちばん遠い SA/PA を選びます。範囲内になければ、範囲を超えた直後の SA/PA で妥協します。
  - 15分以上いる立ち寄り先は休憩とみなし、そこから数え直します。
  - 仕様書にない追加: SA/PA が1つもないまま休憩間隔を超える（一般道など）とき、範囲を超えた SA/PA で妥協したときは、その時間帯を「道の駅やコンビニで休憩を取ってください」と伝えます。
- 区間のカードの「おすすめ休憩地（○件）」に、「休1」などの印、名前、着く時刻の目安、前の休憩からの運転時間を出し、「ここで30分休憩する」で、その SA/PA を「休憩」の立ち寄り先として、ルート上の順番の位置に入れて計算し直します。休憩が要らないときは「休憩間隔内に到着できるため、休憩の提案はありません」と出します。「ルート上のSA/PA（○件）をすべて見る」で、通るすべての SA/PA を出します。おもな設備（仕様書では最大3つ）は、カテゴリ検索の回数を使うので今は出しません。
- **SA/PA の立ち寄り先は、有料道路上の地点として渡します。** 経由地に `"road-type": "toll"` を付けます。付けないと近くの一般道に寄せられ、高速を降りて SA/PA に寄り、また乗り直すルートになります（2026-10-01 に妙高SA で確認。付けないと運転時間が12〜15分増え、付けると距離は経由地なしと同じ 213.57km で、休憩の30分だけ時間が増えた）。休憩の提案から入れたときも、名前で検索して入れたときも（場所の種類が SA/PA なら）同じです。
- 注意: 名前で SA/PA を探すと、反対向き（上り・下り）の SA/PA が選ばれることがあります。帰りのルートに行き方向の妙高SA を入れて試すと、IC で降りて乗り直し、反対車線の SA に寄る大回りのルートになりました。休憩の提案から入れる場合は、その区間のルート上の SA/PA を使うので起きません。

### 7.3 渋滞予測
- RapidAPI では渋滞情報（VICS・プローブ）を使えないため、すべて渋滞を考慮しない時刻で計算します（2026-09-30 確認）。
- 画面に「渋滞を考慮していない時刻です」と表示します。
- 時刻に余裕を足す工夫（例: 行きの到着時刻を早めに提案する）をするかは、段階1で実際の時刻を見てから決めます。

## 8. データの形

TypeScript の型で書きます。細部は作りながら直します。

```ts
type Place = {
  name: string;
  lat: number;
  lon: number;
  spotCode?: string;   // NAVITIME のスポットのコード
  address?: string;
  category?: string;   // 例: 駅、スタジアム。検索結果で同じ名前の場所を見分けるのに使う
};

type StopKind = "sightseeing" | "meal" | "rest" | "other";

type Stop = {
  place: Place;
  kind: StopKind;
  stayMinutes: number;
};

type Hotel = Place & {
  rakutenHotelNo?: number;  // 楽天トラベルの施設番号
  reserveUrl?: string;
};

type LegResult = {
  departAt: string;       // ISO 8601
  arriveAt: string;
  driveMinutes: number;
  distanceMeters: number;
  tollYen: number;
  trafficConsidered: boolean;   // 渋滞予測込みか
  restAreas: { name: string; kind: "SA" | "PA"; lat: number; lon: number; passAt: string }[];
  shape: [number, number][];    // 間引いたルートの形（地図用）
  calculatedAt: string;
  inputHash: string;            // 計算したときの条件。今の条件と違えば「未計算」
};

type Leg = {
  id: string;
  label: string;           // 例: 行き、前日に宿へ、帰り
  from: Place;
  to: Place;
  timeRule: "arriveBy" | "departAt";   // 着く時刻から逆算か、出る時刻からか
  time: string;            // ISO 8601
  stops: Stop[];
  result?: LegResult;
};

type Plan = {
  id: string;
  name: string;
  home: Place;
  venue: Place;
  matchDate: string;       // YYYY-MM-DD
  arriveBy: string;        // HH:mm
  matchEnd: string;        // HH:mm
  exitMinutes: number;
  restIntervalMinutes: number;
  hotelsBefore: Hotel[];   // 前泊（試合日に近い順）
  hotelsAfter: Hotel[];    // 後泊。前日と同じ宿に泊まるときは前泊と同じ場所が入る
  hotelBeforeArriveBy?: string;  // HH:mm 前日に宿泊先へ着く時刻（段階2までのプランには無い）
  hotelAfterDepartAt?: string;   // HH:mm 翌日に宿泊先を出る時刻（同上）
  legs: Leg[];
  createdAt: string;
  updatedAt: string;
  schemaVersion: 1;        // 書き出したファイルを読み込むときの形の確認用
};
```

## 9. 公開と安全

### 9.1 GitHub に載せないもの
- インターンの仕様書（リポジトリの外の `NAVITIME Internship\specification.md`。誤ってコピーしても入らないよう `.gitignore` にも書く）
- `.env` などの API キーを書いたファイル
- 最初のコミットの前に `.gitignore` に書き、`git status` で入っていないことを確認してから push します。一度履歴に入ると、あとで消しても残るためです。

### 9.2 API キーを守る
- NAVITIME と楽天の API キーは、Vercel の環境変数に入れ、サーバー側だけで使います。ブラウザには渡しません。
- 公開した URL を知っていれば、他人もサーバー側の中継を呼べてしまい、無料枠を使われます。これを防ぐため、中継を呼ぶときに合言葉を必要にします。
  - 合言葉は Vercel の環境変数（`ENMATE_PASSPHRASE`）に入れ、サークルのメンバーにだけ伝えます。
  - 初めて検索するときに合言葉を入れてもらい、合っていたらブラウザに保存します（2026-10-02 実装）。はじめは「初めて開いたとき」の予定だったが、閲覧ページと読み込んだプランは API を呼ばないので、見るだけの人に合言葉を聞かないよう、検索するときに変えた。合言葉が違えば聞くのは1回だけで、NAVITIME は呼ばないので使用回数も減らない。
  - ブラウザは合言葉を URL エンコードしてヘッダー（`x-enmate-passphrase`）で送ります（ヘッダーには日本語をそのまま入れられないため）。サーバーはハッシュにしてから比べます。
  - 公開したサーバーで合言葉を設定し忘れたときは、中継を止めます（誰でも呼べる状態にしない）。開発サーバーでは、設定していなければ確かめません。
- 中継は、このアプリで使う API と項目だけを通します（何でも中継できる作りにはしない）。

### 9.3 出典の表示
- 地図の右下に「OpenFreeMap © OpenMapTiles Data from OpenStreetMap」（それぞれのサイトへのリンク付き）を表示します（地図の設定に入っている出典を MapLibre がそのまま出す）。
- 駐車場を表示するときは「© OpenStreetMap contributors」を表示します。
- 楽天トラベル API のクレジット表示の決まりは未確認です（§12）。
- README にも、使っているサービスと出典を書きます。

### 9.4 GitHub で見せるもの（就活向け）
採用担当者は、アプリを動かすより README とコミットの履歴を見ることが多いはずです。動かさなくても伝わる形にします。

| 見せるもの | 中身 |
|---|---|
| README | 解きたい課題（§1）、画面のスクリーンショットか短い動画、使っている技術とサービス、インターン版から変えた点と理由（§3.2）、AI に任せたことと自分が判断したこと、確認したことと未確認のこと |
| この設計書 | `docs/design.md` として置く。仕様書の文章は含めない |
| テストケース表 | 本人が考えた失敗しそうな点と、それを確かめるテスト（§10） |
| コミットの履歴 | 段階ごとに、何をなぜ変えたかが分かるメッセージにする |
| 見本のプラン | 最初から1件入れておく。閲覧ページは API を呼ばないので（§5.4）、合言葉がなくても誰でも公開 URL で見られ、無料枠も減らない |

- README に「インターンで作ったものを、許可を得た範囲の資料をもとに個人で作り直した」と書きます。書き方は、インターン先の許可の範囲を超えない表現にします（§12.2）。
- 公開 URL を README に載せる場合、見本のプランは誰でも見られ、ルート検索などは合言葉が必要、という状態になります。

## 10. テストの進め方

進め方は、本人が「利用場面・期待する結果・失敗しそうな点」を考え、AI が観点を補ってテストコードと実装を書く流れにします。期待する結果は本人が決めます。

### 10.1 機能ごとの手順
1. 利用場面を書く（誰が、何のために、どの操作をするか）
2. 期待する結果を書く
3. 失敗しそうな点を本人が出す
4. テストケース表を作る（AI が不足している観点を補い、本人が期待結果を確認する）
5. AI にテストコードを書かせ、実装させる
6. 自動テストを実行し、何を確かめているテストかを見る
7. 本人が実機で操作する
8. 見つけた不具合をテストに残す
9. 確認したこと、未確認のことを記録する

### 10.2 失敗しそうな点の候補（AI が挙げた観点。本人が採用を決める）
| 観点 | 例 |
|---|---|
| 日付またぎ | 試合が夜に終わり、家に着くのが翌日になる |
| 境界の時刻 | 到着時刻が 0:00 ちょうど、試合終了が到着時刻と同じ |
| 連打 | 「計算する」を連打して、同じ区間を何度も検索する（回数の無駄） |
| 古い結果 | 条件を変えたのに、前の計算結果のまま保存できてしまう |
| 通信の失敗 | ルート検索がエラーになったとき、成功したように見えてしまう |
| 使用回数の上限 | 500回を超えたときに、何が起きたか分からない |
| ファイルの読み込み | 形の違う JSON や、別のアプリのファイルを読み込んだ |
| 通らない都道府県 | 新潟→岡山のプランで、香川の宿を選べるか（§1.3 の実体験） |
| 位置情報 | 当日に位置情報の利用を許可しなかった |

### 10.3 段階1（日帰りプラン）の利用場面・期待する結果・失敗しそうな点

状態: **AI が書いた下書きをもとに実装済み。本人の操作確認待ち**（2026-10-01）。インターン版の動きをもとに AI が書き起こしたものです。2026-10-01 に進め方を変え、先に AI がこの表をもとに作り、本人が実際に操作して、想定と違った点を修正として伝えることにしました（表を先に読んで確定するより、動くものを触るほうが違いに気づきやすいため）。本人が直した点は、この表に反映します。

#### 利用場面
